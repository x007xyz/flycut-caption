# 让 AI 自己维护项目：可复用方案

一套让 coding agent 写代码、审代码、合并、发版、自我复盘的项目结构。可以照搬到其他仓库，按本文的模板填入项目自己的内容即可。

- 参考来源：WquGuru 对 yetone 的 magpie 项目的分析（[原帖](https://x.com/wquguru/status/2109650264601117141)）。
- 落地实例：本仓库 FlyCut Caption。文中「示例」都取自这里，可以对照 `AGENTS.md`、`LESSONS.md`、`docs/` 查看完整文件。

## 1. 核心思路

| 机制 | 作用 |
|---|---|
| **路由表**（`AGENTS.md`） | 本身不写规则，只告诉 agent 做什么事之前读哪份文档，避免一个巨大的规则文件 |
| **错题本**（`LESSONS.md`） | 每晚由 agent 复盘当天的 commit，记录返工、不该合并的、验证太弱的改动 |
| **转正门槛** | 同一条教训在 **3 个不同日期**出现，就从错题本移入代码规范，变成硬规则 |
| **验收标准**（`docs/code-standards.md`） | 合并和发版前逐条对照；其中三条最关键：回退测试、真实使用、没跑的写出来 |
| **已拍板的决定**（`docs/decisions.md`） | 人定的方向，agent 不能在 PR 里推翻 |
| **机器闸门** | CI 全绿才能打 tag；合并绑定审过的 sha |
| **三个 loop** | 修问题、审 PR、夜审并行运行 |

分工：**人管方向、守闸门、处理 UI/UX；写、审、合、发、复盘交给 agent。**

原文没有公开 magpie 的夜审怎么触发、用什么提示词，本方案的夜审脚本和 loop 提示词是补全的设计。

## 2. 目录结构

```text
CLAUDE.md                          # 只引用 AGENTS.md 和 LESSONS.md
AGENTS.md                          # 路由表
LESSONS.md                         # 错题本
docs/
  code-standards.md                # 验收标准 + 已转正规则
  decisions.md                     # 已拍板的决定
  subsystems/<name>.md             # 每个子系统的规则和验证命令
  agent/
    nightly-review-prompt.md       # 夜审提示词
    loops.md                       # 三个 loop 的提示词
scripts/
  release.mjs                      # 发版闸门
  nightly-review.mjs               # 夜审脚本
.github/workflows/ci.yml           # push / PR 的 CI
```

## 3. 落地步骤

按顺序做，前三步是确定性工作，做完立刻有收益；第四、五步需要先积累一两周带验证记录的提交历史，否则夜审没有素材。

| 阶段 | 内容 | 工作量 |
|---|---|---|
| 1 | 拆分文档：路由表、子系统文档、`CLAUDE.md` | 半天 |
| 2 | 写验收标准、已拍板决定、错题本骨架 | 半天 |
| 3 | 加 CI 和发版闸门 | 半天到一天 |
| 4 | 夜审脚本和提示词 | 半天 |
| 5 | 三个 loop | 按需 |

### 阶段 1：拆分文档

1. 把现有的大规则文件（`AGENTS.md`、`CLAUDE.md`、`.cursorrules` 等）里的规则按子系统拆到 `docs/subsystems/<name>.md`。每份文档写：适用范围（路径）、规则、验证命令。
2. 搬的时候顺手检查过时内容：已删除的目录、已换掉的技术方案、「没有测试框架」这类早已不成立的描述。
3. `AGENTS.md` 改成路由表（模板见 [§4.1](#41-agentsmd路由表)）。
4. `CLAUDE.md` 只写两行引用，让 Claude Code 自动加载；Codex 等读 `AGENTS.md` 的工具会通过路由表找到其他文件。

### 阶段 2：验收标准、决定、错题本

- `docs/code-standards.md`：6 条验收标准（模板见 [§4.2](#42-docscode-standardsmd验收标准)）。
- `docs/decisions.md`：架构决定可以从现有文档整理；产品和交互决定必须由维护者本人确认，agent 不要自己编。
- `LESSONS.md`：写好格式说明。如果 git 历史里能找到真实的返工案例（例如「改版本号 → 下一个提交修复构建」），用它做第一条，比空文件更能说明格式。

### 阶段 3：CI 和发版闸门

- CI 在 push 和 PR 时跑验收标准第 1、2 条；平台矩阵与发版平台保持一致。
- 允许 `concurrency` 取消旧运行，但发版闸门只认 `completed + success`，被取消的不算。
- 发版脚本检查通过后才创建并推送 tag（检查项见 [§4.6](#46-发版闸门检查项)）。
- 合并 PR 一律 `gh pr merge --match-head-commit <审过的 sha>`。

**先在干净副本里模拟 CI。** 把仓库文件（`git ls-files -co --exclude-standard`）复制到临时目录，从 `pnpm install` 开始跑一遍。本地能过、干净环境不能过的情况很常见：例如需要先构建的 vendored 包、构建配置里引用了运行时才生成的目录。

### 阶段 4：夜审

1. 脚本收集复盘窗口内的提交，用启发式规则标出可疑项（规则见 [§4.7](#47-夜审启发式规则)）。
2. 把报告和固定提示词交给 agent，**只允许它修改 `LESSONS.md` 和 `docs/code-standards.md`**，只给只读的 git 命令。
3. `--commit` 模式下也只提交这两个文件，不碰工作区里的其他改动。
4. 用定时任务每天凌晨跑一次。

### 阶段 5：三个 loop

各自在独立的 git worktree 里运行（提示词见 [§4.8](#48-三个-loop-的提示词)）。

| Loop | 建议间隔 | 产出 |
|---|---|---|
| 修问题 | 30 分钟 | 每轮一个分支 + 一个 PR，不合并自己的 PR |
| 审 PR | 20 分钟 | 评论、合并，或打 `needs-maintainer` 标签 |
| 夜审 | 每天一次 | 一个只改错题本的提交 |

## 4. 模板

### 4.1 AGENTS.md（路由表）

```markdown
# AGENTS.md

本文件是给 coding agent 的路由表：做什么事之前先读哪份文档。具体规则写在被引用的文档里，不写在这里。

<一两句话说明项目是什么、主要技术栈>

## 每次开工

1. 读 LESSONS.md：之前踩过的坑和照做的做法。
2. 读 docs/code-standards.md：验收标准，写代码和交付前都要对照。

## 按改动范围读文档

| 要改的地方 | 先读 |
|---|---|
| `<路径 glob>` | docs/subsystems/<name>.md |
| 跨多个子系统 | 每个涉及的子系统文档都读，验证要求取并集 |
| 改变已有行为、交互或架构边界 | docs/decisions.md：已拍板的决定不在 PR 里推翻 |

## 按任务读文档

| 任务 | 先读 |
|---|---|
| 写代码、修 bug | 对应子系统文档 + docs/code-standards.md |
| 审查代码或 PR | docs/code-standards.md 逐条对照 + docs/decisions.md |
| 合并、打 tag、发版 | docs/code-standards.md 第 6 条；发版只用 `<发版命令>` |
| 复盘、更新错题本 | LESSONS.md 顶部的「怎么记」、docs/agent/nightly-review-prompt.md |
| 作为 loop 自动运行 | docs/agent/loops.md |

## 常用命令

- `<启动开发>`
- `<lint / 类型检查>`
- `<测试>`
```

`CLAUDE.md`：

```markdown
@AGENTS.md
@LESSONS.md
```

### 4.2 docs/code-standards.md（验收标准）

6 条全部满足才能合并或发版；做不到的按第 5 条写明。

1. **静态检查全绿**：列出 lint、类型检查等命令。
2. **测试全绿**：列出测试命令。main 上已经挂掉的测试视为要马上修的 bug，不能当作「与本次无关」跳过。
3. **Red check（回退测试）**：修 bug 或改行为必须带测试。撤掉本次修复后新测试必须失败，并且失败信息要指出是哪个行为错了。编译失败、测试被跳过、断言与改动无关都不算。纯重构说明哪些现有测试覆盖了改动路径即可。
4. **真实使用**：按改动范围列一张表，写清每类改动至少要做的真实验证（真实账号、真实接口、真实设备、真实素材）。没实测过的功能不在上面继续开发，也不对用户说「已修好」。修用户报告的问题时，先在报告人用的那个界面原样复现。
5. **没跑的写出来**：commit 正文和 PR 评论都带固定格式的验证记录（见 §4.3），`Not run` 不能省略。
6. **合并与发版**：合并绑定审过的 sha；打 tag 前该 commit 必须有完成且全绿的 CI；发版只用发版脚本；列出需要保持一致的版本号文件。

再加两节：

- **代码约定**：跟随所在文件的写法；同类 bug 一起修；不推翻 decisions.md；安全相关路径（权限配置、执行外部二进制的脚本、鉴权）不自动合并。
- **已转正规则**：初始为空，由错题本转入，每条保留原来的证据。

### 4.3 验证记录格式

```text
Verification (@ <commit sha>):
- Ran: <命令> ✅, <命令> ✅
- Red check: 撤销 <文件> 的修复后，<测试名> 失败于 "<具体行为>"
- Real use: <在什么环境做了什么操作，结果如何>
- Not run: <检查项>（<原因>）
```

`Ran` 必须对应 `@` 后面的 commit；代码之后又改过就重跑。

### 4.4 docs/decisions.md（已拍板的决定）

```markdown
# 已拍板的决定

PR 不要推翻这些决定；确实需要改，先在 PR 描述里说明理由，等维护者确认后再动手，并同步更新本文件。

格式：一句决定 + 原因 + 来源（commit / issue / 文档 / 维护者确认日期）。

## 架构
- **<决定>。** <原因>。来源：<...>。

## 产品定位与优先级
| 优先级 | 能力 | 状态 |
|---|---|---|
| P0 | <最基础的能力> | <已有 / 规划中> |

### P0 <能力>
- **<决定>。** <原因>。

## 交互
- <快捷键、默认值等不希望被顺手修改的行为>
```

写法要点：

- 优先级表要写明「前面的没做稳之前，不为后面的功能牺牲它，也不跳级开发」。
- 每项能力写「范围内 / 范围外」，范围外的同样是决定。
- 还没决定的事写成「待维护者确认：……确认前不要开发」，不要让 agent 自己猜。
- 涉及授权、隐私的能力（例如声音克隆、上传用户数据）要写明授权确认、数据归属、上传前告知；默认值也要写死（例如「AI 生成内容标注默认开启」）。

### 4.5 LESSONS.md（错题本）

```markdown
# LESSONS

agent 每次开工前读这份文件。它是错题本：记录返工过的、不该合并的、验证太弱的改动，以及值得照做的做法。

## 怎么记

每条格式：

### <一句规则，祈使句>
Why: <一段原因，说清楚当时发生了什么>
Evidence: <commit sha / issue / PR>
Seen 1× (YYYY-MM-DD)

- 复盘时只看三类问题：修完又返工的、压根不该合的、验证做得太糙的。
- 已有条目再次出现：在 Seen 上加一次并追加日期，Evidence 追加新的 sha。同一天多次只算一次。
- 出现在 3 个不同日期后，把规则移到 docs/code-standards.md 的「已转正规则」，这里只留标题和一行 `→ promoted to code-standards.md (YYYY-MM-DD)`。
- 做对的事也记，标题前加 `Done right:`。

## Lessons
```

示例条目（来自本仓库）：

```markdown
### 改版本号后在提交前跑一次 `cargo check`
Why: 2.0.2 的版本号提交在 src-tauri/Cargo.toml 的 version 后面多了一个逗号，TOML 不允许，导致 Windows 发版构建失败，紧接着又补了一个修复提交。
Evidence: 0367682 → ad00f06
Seen 1× (2026-07-10)
```

### 4.6 发版闸门检查项

发版脚本（示例：`scripts/release.mjs`，支持 `--dry-run`）逐项检查，全部通过才创建并推送 tag：

- [ ] 在主分支上
- [ ] 工作区干净
- [ ] HEAD 已推送到远端主分支
- [ ] 要打的 tag 本地和远端都不存在
- [ ] 所有需要手动维护的版本号一致
- [ ] 版本号所在的配置文件能被工具正常解析（例如 `cargo metadata`）
- [ ] 该 commit 在 CI 工作流里有一轮 `completed + success` 的运行（`gh run list --workflow ci.yml --commit <sha>`）

能从单一来源派生的版本号就不要手动维护。示例：前端库导出的 `version` 由 Vite 的 `define` 从 `package.json` 注入，不再写死。

### 4.7 夜审启发式规则

脚本先用规则粗筛，再交给 agent 看实际 diff 判断，规则会漏报也会误报：

| 规则 | 判定 |
|---|---|
| 疑似返工 | `fix` / `revert` 提交改到的文件，在它之前 72 小时内被别的提交改过 |
| 缺验证记录 | 非纯文档提交的正文里没有 `Verification` 段 |
| 缺回退测试 | `fix` 提交有验证记录但没有 `Red check` |
| 有未运行项 | 验证记录里有 `Not run`，列出来供 agent 判断是否关键 |

夜审提示词要点：

- 先读错题本、验收标准、已拍板的决定。
- 用 `git show` 看实际改动，只判断返工、不该合并、验证太弱三类问题；做得好的记为 `Done right`。
- 先找已有条目合并计数，不写近义的重复条目。
- 证据必须是真实存在的 sha / issue / PR，不能编造；拿不准的不写；没有发现就不改。
- 满 3 个不同日期就转正。
- 最后输出：新增了什么、哪些计数 +1、是否转正、看过但判断不算问题的可疑提交。

agent 的权限：

```text
--permission-mode acceptEdits
--allowedTools "Read,Grep,Glob,Edit(LESSONS.md),Edit(docs/code-standards.md),Bash(git log:*),Bash(git show:*),Bash(git diff:*)"
```

### 4.8 三个 loop 的提示词

**修问题**

```text
按 AGENTS.md 的路由读文档。从 issue 中挑一个未分配、没有关联 PR、不带 needs-maintainer 标签的（优先 bug，再按 docs/decisions.md 的优先级）。
在报告人使用的界面上先复现；复现不了就在 issue 下说明你试过什么，然后结束本轮。
从主分支新建分支修复，按 docs/code-standards.md 完成全部验收，commit 正文带 Verification 段。issue 来自用户原话的，commit 标题括号里原样保留那句话。
推送并开 PR，描述写清楚复现步骤和 Verification。不要合并自己开的 PR。一轮只处理一个 issue。
```

**审 PR**

```text
按 AGENTS.md 的路由读文档。列出未合并、没有 needs-maintainer 标签、你还没审过当前 head 的 PR，一次审一个。
逐条对照 docs/code-standards.md 和 docs/decisions.md。自己在本地跑一遍 Verification 声称跑过的检查，并亲自做一次 Red check。
- 全部满足：评论写明在哪个 sha 上跑了什么，然后 gh pr merge --squash --match-head-commit <审过的 sha>。
- 有问题：逐条指出不满足的条目，不合并。
- 改了安全相关文件、推翻了 decisions.md、或需要真实账号 / 真机而你做不到：打 needs-maintainer 标签并说明原因，不合并。
```

**夜审**

```text
在主分支最新提交上运行 <夜审命令> --commit，然后 git push。脚本报错就说明原因，不要手工改 LESSONS.md 绕过脚本。
```

## 4.9 界面与设计系统

需求流程不设单独的交互原型阶段：AI 写代码之后改界面很便宜，先做原型再写正式代码等于同一个界面确认两次。界面质量靠三处保证：

- **PRD 把每个界面状态写成 AC**（空、加载中、正常、出错……），状态怎么处理在 PRD 里定，不留给写代码时临时决定。
- **开发直接写真实代码**，不另做假数据版本。
- **验收用端到端测试覆盖每个状态和明暗主题，并截图**，维护者看截图确认。
- **从零开始的项目**，在第一个有界面的需求之前先建立设计系统，写一份 ADR：
  - 技术栈：推荐 React + Tailwind + shadcn/ui（组件源码复制进项目，可以随意修改；底层 Radix 保证可访问性）；
  - 基础样式值：颜色、字号、间距、圆角、明暗主题；
  - 基础组件和一个组件展示页。
  这一步本身可以作为一个需求走流程。
- **方向还不清楚时**，可以先用独立 HTML 或 Artifact 页面做几版低保真探索，看完就扔，结论写进 PRD。

## 5. 迁移到其他项目的检查清单

- [ ] 现有规则文件已拆分，`AGENTS.md` 只剩路由
- [ ] 每个子系统文档都有适用路径和验证命令
- [ ] 过时描述已清理
- [ ] `code-standards.md` 第 4 条的「真实使用」表已按本项目填写
- [ ] `decisions.md` 的产品与交互部分由维护者本人确认
- [ ] CI 已在干净副本里模拟通过，并合入主分支
- [ ] 发版脚本 `--dry-run` 能正确拦截不合格的状态
- [ ] 夜审脚本 `--report-only` 用历史提交试跑过，能识别出已知的返工
- [ ] 夜审 agent 的命令可执行（脚本里可用环境变量指定路径）
- [ ] 仓库已创建 `needs-maintainer` 标签
- [ ] 定时任务已创建（需维护者确认后再建）

## 6. 注意事项

- **刚引入时，历史提交都会被标为「缺少验证记录」。** 这是预期结果，夜审只复盘最近 24 小时，不会追溯。
- **依赖模型、账号等外部资源的测试在 CI 里通常会自动跳过，结果仍显示通过。** 不要把这当作已验证，要在本地验证并写进 `Not run`。
- **跑 loop 的环境要能做「真实使用」验证。** 做不到的话，所有 PR 都会落到 `needs-maintainer`，loop 就失去意义。
- **发版闸门要先于 loop 上线。** 没有闸门时，agent 的高频改动会直接变成高频发版（magpie 曾在一天内发了 168 个版本）。
- **夜审只改错题本，不改代码。** 改代码是修问题 loop 的事，分开才能让每个提交的职责清楚。
