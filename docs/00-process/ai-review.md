# AI 审查清单

交给维护者的文件，先由独立的 AI 审查员审过。审查员不是写这个文件的 agent：另起一个子代理或会话，只给它文件路径和这份清单，让它自己读代码和文档核对，不要把作者的结论喂给它。

审查员逐条核对，只报不满足的条目和具体位置（文件、行、AC 编号）；全部满足就写「通过」。主会话看过审查结果后记录：

```bash
pnpm feature ai-review F-0001 --by <审查员> [--stage <阶段>]            # 通过
pnpm feature ai-review F-0001 --by <审查员> --fail "<不满足的条目>"     # 不通过
```

不通过：作者改完再审，最多两轮。两轮还不过的问题写进批次文件对应节点的「AI 审查结论」，交给维护者；不要为了过审删掉内容或把问题改写得含糊。

审查员能自己确认的就自己确认，不要把下面「留给人」以外的事推给维护者。

## 留给人工节点的事

只有这些必须留给维护者，审查员发现了就标出来写进批次文件，不要自己定：

- 需求范围、AC 的增删和语义；待澄清的问题。
- 推翻 `docs/decisions.md`，或改前面需求已经定好的共用契约（数据格式、RPC、存储结构）。
- 新的 ADR（`proposed`）。
- 对外或不可逆的操作（发版、推送到公共渠道、删除用户数据）。

## 01-spec 需求说明

- [ ] 来源原样引用并注明日期；问题只写问题，对应 `vision.md` 里的哪类口播创作者写清楚。
- [ ] 范围有「做」和「不做」；和 `docs/decisions.md` 没有冲突，或冲突已列为待澄清问题。
- [ ] 每条 AC 编号、可验证（当……时，系统应……），注明界面和 Provider；每个新增或改动的界面，每个状态（空、加载中、正常、出错、冲突……）各有一条 AC，中英文关键文案齐全。
- [ ] 竞品与获客的资料有来源和日期，没核实的写「待核实」，没有编造。
- [ ] 规模检查：AC 约 10 条以内、可单独发布、约两周；超了要在结论里建议怎么拆。
- [ ] `depends_on` 和 Epic 候选表一致，没有漏掉明显的依赖。
- [ ] 待澄清的问题每条都有建议答案；没有把该问的事自己假设了答案。
- [ ] spike：写的是「要回答的问题」，每个问题能被调研回答。

## 02-design 技术设计

- [ ] 「验收标准覆盖」表覆盖每一条 AC，没有遗漏或编造 AC。
- [ ] 遵守涉及子系统文档的规则（按 `AGENTS.md` 路由表核对），例如新 RPC 由插件注册并在 `shared/protocol.ts` 声明、Tauri 只做外壳。
- [ ] 有至少一个备选方案和取舍；推翻已有决定或共用契约的地方已标出。
- [ ] 实现清单按功能纵向切、按依赖排序、每项能单独验证；几个需求共用的契约放在第一项。
- [ ] 验证计划逐条 AC 写了目标平台、自动化命令和断言，符合 `docs/30-engineering/acceptance-testing.md`；需要实机的写明原因。
- [ ] 和同批次其他需求的设计不冲突（改同一个文件、同一个契约时说清楚谁先定、谁跟随）。

## 02-research 调研报告

- [ ] 「要回答的问题」逐条有结论。
- [ ] 评估标准先定、候选方案按标准比较；资料有来源和日期，查不到的写「待核实」。
- [ ] 实验的数据、命令和脚本在仓库里，写明路径，能复现；结论和实验结果一致。
- [ ] 「对后续需求的影响」已更新所属 Epic 候选表和依赖它的需求说明；改了范围或写了 ADR 的已列进批次文件，留给下一个人工节点。

调研报告通过 AI 审查就算确认，不再单独请维护者确认。

## 04-test-report 测试与验收

- [ ] 报告开头的 commit sha 存在，且是当前代码；之后有改动就要重新验收。
- [ ] 每条 AC 都有一行：目标平台、测试名（带 AC 编号）、命令、结果；审查员**自己重跑**至少报告里的自动化命令和一个 Red check，结果一致。
- [ ] 桌面专属行为没有用 Web 结果代替；`⏸ Not run` 都写了原因，没有把没跑的写成通过。
- [ ] 涉及界面的 AC 有截图证据，覆盖需求说明列出的状态和明暗主题。
- [ ] 回归检查跑了 `docs/code-standards.md` 第 1、2 条的全部命令。
- [ ] 「自行决定的事项」汇总了 02、03 里记下的每一条；需要拍板的标了「请确认」。
- [ ] 结论和逐条结果一致：有 ❌ 不能写「可以发布」。
