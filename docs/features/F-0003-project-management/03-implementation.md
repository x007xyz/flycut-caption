## 自行决定的事项

<!-- 开发中自己决定的事：决定了什么、为什么、影响哪条 AC。验收时汇总进测试报告 -->

- **整个实现一次提交**：清单 1–7 共用同一份格式 2 契约和同一个 `projectService`，按项拆提交会产生大量只能一起工作的中间状态；改为一次提交实现，再单独提交文档和验收（流程要求每项一提交，这里偏离）。
- **重命名、移到回收站、恢复不比较修订号**（后写的生效）：AC 只要求保存类操作检测冲突；去掉设计里的 `metadataRevision`（AC-2、AC-3、AC-4）。
- **名称排序用 `Intl.Collator(界面语言)`**：中文界面下汉字按拼音、排在拉丁字母之前，这是 ICU 中文排序规则（AC-6）。
- **画幅只指 `aspectPreset`**：底边距等其余字段属于样式，跟随项目时共享；新加入的视频还没保存过画幅时，仍按画面尺寸推断画幅（会顺带改底边距，与 F-0002 相同）（AC-13）。
- **一次性样式提示按项目记在本机 localStorage**（界面偏好，不进 Host）（AC-31）。
- **项目已彻底删除后的「另存为新项目」**：新增 `projects.createFromSnapshot`，只保存字幕、修改和样式，媒体读作丢失，用户按 F-0002 媒体丢失流程重新选择文件；不尝试让外壳重新登记原路径（ADR-0002 只允许本次选择或拖入的文件）（AC-32）。
- **桌面端多选**：外壳新增 `pick_media_files`（rfd 多选），选中的路径同样登记到允许列表（AC-8）。
- **切换视频时样式不当成修改**：载入目标视频前先切换当前项目、清空保存起点，避免把新视频的样式写进上一个视频（AC-10）。
- **F-0002 的端到端测试改用格式 2 的假数据**：自动保存改走 `saveVideoEdits`，跟随项目的视频不再写自己的 `stylePair`；测的行为不变。

## 与设计的偏差

<!-- 实现时改变了设计的地方及原因；重大偏差回到 02-design.md 修改，并记进测试报告 -->

ADR-0003 已按实际实现改写，下面几条请维护者在验收时确认：

1. **没有项目事务恢复记录**：每个文件仍是 `.tmp → rename` 原子替换，保存先写 `edits.json` 再写 `project.json`。中途崩溃时最坏情况是 `edits.json` 已是新内容而修订号没加一，读到的是较新的数据，不会读到半个文件；代价是此时另一个窗口用旧修订号保存同一视频不会被判为冲突（那次保存对用户来说本来就显示为失败并会重试）。
2. **迁移改为读时计算**：不搬动文件、不做迁移事务。格式 1 的样式留在第一个视频的 `edits.json`，项目没有 `style` 时由 Host 读出；第一次写入时保留 `project.v1.json`。移除提供样式的视频前先把样式写进 `project.json`。
3. **没有 `metadataRevision`**：重命名等元数据操作后写的生效（见自行决定）。
4. **Host 不记录转写属于哪个视频**：「转写中不能切换、不能移除」只在发起转写的窗口的界面上限制；另一个窗口仍可以移除正在转写的视频，此时转写结果写回会失败（视频已不存在），不会写到别的视频。
5. **彻底删除先改名再删**（`projects/.purge-*`），启动时清理残留，代替设计里的「清理标记」。

## 遗留问题

- **切换到 60 分钟视频未达成功指标**：3 次实测 3.5 / 4.4 / 5.0 秒（指标 3 秒）。`projects.open` 97 ms 返回（2.3 MB），之后约 3.3 秒是前端载入和渲染 1173 条字幕（字幕列表没有虚拟化）。与 F-0002 记录的「60 分钟数据打开 6.9 秒」同一根因，不是本需求引入的；建议单独立项做字幕列表虚拟化。
- **桌面端（Tauri）没有实际运行**：`pnpm tauri:dev` 使用本机真实的应用数据目录，第一次保存就会把维护者现有项目升级为格式 2（保留 `project.v1.json`），需要维护者同意后再测；原生多选、拖入添加、逐段导出未在桌面端验证。
- **真实导出没有逐段验证**：导出沿用 F-0002 的按当前视频导出，本需求没有改导出代码，未实际导出各段并用播放器检查。
