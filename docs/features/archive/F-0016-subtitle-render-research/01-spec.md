# F-0016 字幕渲染方案调研：需求说明

> 需求说明合并了立项和产品文档，是这个需求的第一个确认点；调研类需求的第二个确认点是调研报告（`02-research.md`）。

## 来源

- Epic 候选 E-03/1「字幕渲染方案：按上表比较 A–E，选定预览与导出一致的渲染架构，写 ADR」，路线图阶段二第 1 项。
- 维护者原话（2026-11-05）：「先调研 E-03/1」。
- 维护者原话（2026-11-05，审阅需求说明时）：「先只考虑当前环境吧，但是需要同时处理 后端渲染和前端展示的问题」。
- 相关决定：`docs/decisions.md`「P2 字幕特效 · 预览与导出一致」——渲染方案由 E-03/1 调研后用 ADR 确定，要求桌面端、Web 端、CLI / MCP 和 Cloud 都能导出（维护者 2026-11-05 确认调研范围）。

## 要解决的问题

面向 `docs/10-product/vision.md` 的首批用户：对着镜头讲的个人口播创作者，单人单机位、10–60 分钟、中文为主，成片发抖音、视频号、小红书、B 站、YouTube Shorts。这类视频的字幕是观感的一大部分，平台上流行逐字高亮、关键词强调、逐字弹出等动态字幕。

现在 FlyCut 的预览和导出是两套渲染：

- **前端展示**：播放器预览用 Canvas 2D 自己绘制（`src/subtitle/subtitleRenderer.ts`、`subtitleLayout.ts`、`subtitleMetrics.ts`）；
- **后端渲染**：导出时生成 ASS，交给 Host 里 FFmpeg 的 libass 硬烧（`src/subtitle/burnAss.ts`）。

静态样式靠两边各写一遍保持一致。加入动画、图片、渐变后，两套实现几乎不可能逐帧对齐，用户会遇到「预览里好看，导出来不一样」，而 decisions.md 已规定只做了预览的特效不算完成。同时，动态字幕对前端预览本身也有要求：播放时要跟得上视频、拖动进度条要立刻显示对应帧，否则用户没法边看边调。

E-03 后面的逐字高亮、关键词强调、平台预设（E-03/2–5），以及 E-07 的竖屏短片导出，都要先有一个同时解决「前端怎么画」和「后端怎么画」的渲染架构，否则每个特效都要写两遍、对齐两遍。

## 竞品与获客

- 剪映、CapCut、Descript、Submagic 等都提供逐字高亮、关键词强调类动态字幕模板；它们各自用什么渲染架构不公开，**待核实**，本调研不依赖竞品内部实现。
- 开源参考（调研阶段记录一手来源和读取日期）：Remotion（网页渲染导出，公司用户需付费许可，具体条款**待核实**）、Revideo（MIT）、FFCreator（MIT，近两年无更新，**待核实**）、JASSUB（libass 的 WASM 移植，MIT）、lottie-web / Skottie / rlottie。
- 获客：本身不直接对用户可见；它决定 E-03/2–5 的动态字幕能否「预览所见即导出所得」，而动态字幕是教程视频和平台展示里最直观的卖点。

## 优先级与依赖

- P2（`docs/decisions.md` 优先级表：字幕特效）。阶段二第 1 项，E-03/2、E-03/3、E-03/5 都依赖它。
- 无需求依赖（`depends_on: []`）。调研可以与阶段一的开发并行；调研结论落地（替换现有预览和导出）属于后续需求，不在本项。
- 外部前置条件：20 分钟和 60 分钟的 1080p 口播素材（建议复用 F-0001 的样本，见待澄清问题）。

## 测试环境

按维护者 2026-11-05 的要求，**本轮只在当前环境实测**：

| 端 | 环境 |
|---|---|
| 前端展示 | 维护者这台 Mac（macOS 26.6.2，Apple Silicon arm64）：Tauri 桌面端的 WKWebView；`pnpm dev` 打开的浏览器页面（Chrome、Safari）作为 Web 端参考 |
| 后端渲染 | 同一台 Mac 上的 Host（Node），使用随仓库打包的 FFmpeg（`src-tauri/binaries`） |

Windows（WebView2）和 Linux / Cloud（无头环境）**本轮不实测**。调研报告对每个方案写明「在这两端可能遇到的问题」（依据文档和依赖说明，标注为未验证），推荐方案在后续落地需求里再补这两端的实测。

## 范围

### 做

- 按 Epic E-03「要比较的方案」表，对方案 A–E 各写一个**一次性原型**，每个原型都必须**同时包含前端展示和后端渲染两部分**，用同一组测试字幕和动画：
  - 静态样式：现有预设里的 3 种（含描边、阴影、底框）；
  - 动画：逐字弹出（带回弹缓动）、逐字高亮、关键词放大、渐变填充、一个图片 / emoji；
  - 三种画幅：横屏、9:16、1:1。
- **前端展示**部分：把原型字幕叠加到现有播放器的视频上，测实时播放、拖动进度条（seek）、暂停时单帧显示、切换画幅；记录帧率、掉帧和 CPU / 内存。
- **后端渲染**部分：由 Host 在没有窗口的情况下导出带字幕的成片（从 Node 脚本或 Host RPC 触发，不依赖前端页面打开），记录导出耗时、CPU / 内存。
- **两端一致性**：对同一时间点，比较前端截图与导出帧的差异，重点看中英混排的字宽、换行和标点挤压。
- 其余 Epic 评测维度：打包（安装包体积增量、原生依赖在 macOS 上能否随 Host 打进 Tauri 包）、动画能力、转场可扩展性（能否用同一份 GLSL 在前后端实现一个转场）、许可。
- 「考虑过但不实测」的方案（Rust→WASM 自研引擎、MLT / GStreamer GES、纯 FFmpeg 滤镜）只写一段说明为什么不实测。
- 产出 `02-research.md`（逐题回答下面的「要回答的问题」，附数据、截图、复现命令、来源和日期）和一份 ADR（`pnpm feature adr`），写明：
  - 选定方案，以及与「桌面导出只走 Host」「Tauri 只做桌面外壳」两条决定的关系；
  - 前后端共用的图形层接口草案：输入时间点 + 字幕 / 动画数据，输出一帧；前端和后端各自怎么调用它；
  - 动画参数的数据格式草案（关键帧、缓动、按字 / 按词的时间偏移），不写死在绘制代码里；
  - 现有 Canvas 预览 + ASS 硬烧怎么迁移、软字幕（SRT / ASS 文件导出）是否保持不变；
  - Windows、Linux / Cloud 尚未实测的风险和补测计划。
- 根据结论，提出落地需要拆成哪几个后续需求（例如「前端预览接入新图形层」「Host 导出接入新图形层」「Windows / Cloud 补测」），回写到 Epic E-03 的候选表建议里，由维护者确认后再立项。

### 不做

- 不在 Windows、Linux / Cloud 上实测（见「测试环境」）。
- 不把任何原型合并进产品代码，不替换现有预览和导出；落地另立需求。
- 不实现 E-03/2–5 的任何特效功能，不做样式编辑界面。
- 不做 B-roll、转场功能本身，只验证所选架构能容纳它们。
- 不评估 Web 端本地回退引擎（WebAV / ffmpeg.wasm）作为正式导出路径；按 decisions.md，它只是回退。
- 不为了通过评测改动现有字幕数据结构；数据格式只出草案。
- 不评测付费商业渲染服务。

## 用户故事

## 验收标准

调研类需求不写 AC，改写「要回答的问题」。调研报告对每题给出结论、数据和证据（全部在「测试环境」一节的 Mac 上测得）；做不到的如实写「未验证」及原因，不用推测代替实测。

- **Q1 前端展示性能**：各方案在 Tauri WKWebView 和浏览器里叠加到 1080p 视频播放时，能否稳定跟上视频帧率（30 / 60 fps）？掉帧比例、CPU、内存是多少？拖动进度条后多久显示出正确的字幕帧？暂停时单帧是否和播放时一致？
- **Q2 两端一致性**：同一组字幕和动画、同一时间点，前端截图与 Host 导出帧的差异有多大（建议指标：文字包围盒偏移像素 + 换行位置是否相同 + 逐像素差异比例）？中英混排的字宽、换行、标点挤压是否一致？WKWebView 和 Chrome 之间是否也有差异？
- **Q3 后端导出性能**：20 分钟和 60 分钟 1080p 口播素材、字幕持续变化时，各方案的总导出耗时、相对实时的倍数、峰值 CPU 和内存是多少？和现有 ASS 硬烧比慢多少？
- **Q4 无界面导出**：各方案能否只由 Host 完成导出，不需要打开前端页面或窗口（为 CLI / MCP / Cloud 做准备）？在 macOS 上需要什么额外依赖？推测在 Linux / Cloud 上还需要什么（标注未验证）？
- **Q5 打包**：在 macOS 上，安装包体积增加多少？原生依赖（例如 `@napi-rs/canvas`、headless-gl）能否随 Host 打进 Tauri 安装包并构建通过？推测 Windows 上的构建风险（标注未验证）？
- **Q6 动画能力**：逐字弹出（回弹缓动）、逐字高亮、关键词放大、渐变填充、图片 / emoji 各方案能否在前后端都实现，实现难度如何？
- **Q7 转场可扩展性**：能否用同一份代码（例如 gl-transitions 的 GLSL）在前端预览和后端导出两边实现转场？代价是什么？
- **Q8 许可与已有决定**：各方案及依赖的许可证是什么？有没有禁止商用、对公司收费或 AGPL 传染的？字体（Noto Sans SC、Inter）在导出端的授权是否覆盖？方案 B 在桌面端用隐藏 WebView 渲染导出帧，是否违反「桌面导出只走 Host」「Tauri 只做桌面外壳」？如果违反，有没有不违反的变体（例如 Host 驱动无头浏览器）？
- **Q9 推荐方案与接口**：推荐哪个方案（或组合，例如 A + E）？前后端共用的图形层接口和动画数据格式草案是什么样？现有预览和 ASS 硬烧怎么迁移，软字幕导出是否不变？
- **Q10 后续拆分**：落地推荐方案需要哪几个后续需求（含 Windows、Linux / Cloud 补测），各自的依赖关系是什么？

## 约束、风险与影响

- **只测一个环境的风险**：WebView2、Linux 无头 Chromium、Linux 上的 Skia 字体光栅化都可能和 macOS 不同。本轮结论只对当前 Mac 成立，ADR 必须写明这一点，后续落地需求要先补测其他端再宣称三端一致。
- **与已有决定的关系**：方案 B 的桌面端变体（隐藏 WebView 截帧）可能与「桌面导出只走 Host」「Tauri 只做桌面外壳」冲突，调研在 Q8 回答，不在本需求里推翻已有决定；如果结论是需要调整决定，按 decisions.md 的流程单独请维护者拍板。
- **打包风险**：Host 随 Tauri 打包，原生 Node 模块（Skia、headless-gl）可能增加构建难度和安装包体积，这是方案 A / C 的主要风险。
- **一致性的根本难点**：浏览器（WKWebView、Chromium）和 Host 端（Skia）的字体光栅化、字距、换行可能不同；同一份 Canvas 代码不等于同一份像素。调研必须实测，不能凭「同一份代码」就认定一致。
- **前端性能的根本难点**：逐字动画需要每帧重绘，长字幕段、多行和描边阴影可能让 Canvas / WebView 掉帧；需要在真实 1080p 视频播放时测，不能只测空白画布。
- **许可**：Remotion 对公司用户收费；FFCreator 停更；调研报告逐项写来源和读取日期。
- **素材与隐私**：测试素材用维护者自有或许可明确的口播素材；不上传第三方服务。
- **影响**：本需求不改产品代码。ADR 确定后会影响 `src/subtitle/**`、播放器预览、Host 导出插件、Tauri 打包和 Cloud 部署，具体在后续需求中处理。
- **验证规范**：按 `docs/code-standards.md`，未执行的测量写「Not run」及原因。
