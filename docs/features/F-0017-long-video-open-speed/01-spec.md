# F-0017 长视频打开提速：需求说明

> 需求说明合并了立项和产品文档，是这个需求的第一个确认点；第二个确认点是测试与验收（调研是调研报告）。

## 来源

E-02/9（本次在 E-02 候选表里补的一行）。两个已做完需求的测试报告都没达到同一条成功指标，都建议单独立项：

- F-0002 测试报告，2026-11-05：「60 分钟数据（1200 句、36000 字）从点击到可编辑 6.9 秒，指标是 3 秒。Host 只占约 65 ms；时间在前端——字幕列表没有虚拟化（1200 条全部渲染文本框），`historyStore.setTranscript` 还把整份转写打印到控制台。……建议单独立项做字幕列表虚拟化。」（[04-test-report.md](../F-0002-project-persistence/04-test-report.md)）
- F-0003 测试报告，2026-11-05：「切换到 60 分钟视频到可编辑：3521、4392、4982 ms ❌（指标 3 秒）。`projects.open` 97 ms 返回，其余约 3.3 秒是前端载入和渲染全部 1173 条字幕。」（[04-test-report.md](../F-0003-project-management/04-test-report.md)）

两条成功指标原文：F-0002「打开一个 60 分钟视频的项目，从点击到可编辑不超过 3 秒（桌面端，本机 Host）」；F-0003「在编辑器里切换视频到可编辑不超过 3 秒（桌面端，本机 Host，60 分钟视频）」。

## 要解决的问题

口播创作者（[vision.md](../../10-product/vision.md) 的首批用户）里，做课程、播客、直播回放和长访谈的人，单条素材常常有 30–60 分钟。他们打开这样的项目，或者在一期的几段视频之间切换时，要等 3.5–7 秒界面才有反应，期间点击和输入都没有响应，看起来像卡死了。F-0003 之后一个项目放多段视频，来回切换是常规操作，每次都要等这么久。

现在的情况（代码与两份测试报告）：

- Host 的 `projects.open` 约 65–100 ms 就返回，慢在前端载入和渲染。
- 「编辑」视图（`SubtitleList`）把每一句未删除的字幕都渲染成一行，每行有一到两个文本框，60 分钟约 1200 行同时渲染。
- 载入转写时（`historyStore.setTranscript`）会把原始和规范化后的整份转写逐条打印到控制台，60 分钟数据有约 2–3 MB。这也意味着字幕全文会出现在开发者工具里。
- 时间轴、播放器、「原语言」视图（字词级，60 分钟约 1.5 万个字词）在这条路径上各占多少时间还没有拆开量过。

## 竞品与获客

- 剪映、Descript 都以长视频文字剪辑为卖点，打开长项目的实际耗时没有公开数据，**待核实**（没有实测）。
- 这是体验底线而不是卖点，不对应单独的获客渠道；但口播长视频是目标用户的典型素材，打开就卡会直接影响试用后是否留下（vision 的「留存」指标）。

## 优先级与依赖

- P0（[decisions.md](../../decisions.md#产品定位与优先级)：转写 + 添加字幕的底座，「已有，持续打磨」）。两个已验收需求的成功指标都卡在这里，后面的 F-0012 校对体验、F-0013 AI 纠错都在同一个编辑器上工作，长视频下也会受影响。
- 依赖 F-0002（项目打开路径）、F-0003（项目内切换视频）。F-0003 还在验收中：**开发要在 F-0003 合并之后的分支上做**，需求说明可以先确认。
- 与 F-0012（校对体验）有交集：F-0012 的「查找、上一处 / 下一处定位」需要把指定的一句滚到可视区。本需求要提供这个能力，F-0012 直接使用；两边谁先做都可以，后做的一方适配。

## 范围

### 做

- 从点击打开项目 / 切换视频，到字幕可编辑，这条前端路径上的所有环节：载入转写、字幕列表渲染、时间轴、播放器初始化等，哪个慢改哪个，目标是 60 分钟素材 3 秒内可编辑。
- 「编辑」视图的字幕列表只渲染看得到的部分（及上下少量缓冲），长列表滚动流畅。
- 去掉载入时把整份转写打印到控制台的做法（性能和隐私两方面）。
- 转写刚完成、字幕第一次载入，走的是同一条路径，一并达到同样的指标。
- 保证编辑、删除、恢复、全选、批量删除、撤销重做、智能剪空白、AI 纠错 / 翻译写回、自动保存、播放高亮在长列表下行为不变（包括不在可视区内的句子）。
- 提供「把第 N 句滚到可视区」的能力，用于播放自动跟随（AC-8）和 F-0012。
- 一个可重复的性能测试：仓库里能重建 60 分钟测试素材 / 数据，用 Playwright 驱动前台 Chrome 计时，结果写进测试报告。

### 不做

- Host 端的读写性能（已经在 100 ms 以内）。
- 转写速度、导出速度。
- 超过 60 分钟（例如 2 小时）素材的指标：只记录实测数字，不设门槛。
- 查找替换（F-0012）。
- 「原语言」视图的提速：只测量切换耗时并写进测试报告，超过 3 秒就在 E-02 补候选需求（问题 3）。
- 改变字幕行的外观和交互（行高、展开文本框、按钮位置都保持现状）。

## 用户故事

- 作为做长视频的口播创作者，我想要打开 60 分钟的项目后几秒内就能开始改字幕，以便不用对着卡住的界面等。
- 作为一期录了好几段的创作者，我想要在项目里的几段视频之间快速切换，以便对照着校对和粗剪。

## 验收标准

测量口径（适用于 AC-1–3）：「可编辑」指字幕列表已显示第一屏、第一句的文本框能获得焦点，输入的字符立即出现，且之后 1 秒内界面没有超过 200 ms 的卡顿（长任务）。测试数据是两段 `tests/media/external` 里的 COSCUP 演讲拼成的约 60 分钟视频（约 1200 句、1.5 万字词），本机 Host，用 Playwright 驱动**前台**本机 Chrome（内置浏览器面板隐藏时定时器被节流，数据不可信），每项测 5 次。

**性能**

- **AC-1 打开项目**：Web 端和桌面端，在首页点击一个只含这段 60 分钟视频的项目，到可编辑，5 次都不超过 3 秒。
- **AC-2 切换视频**：在含这段 60 分钟视频和至少一段短视频的项目里，从编辑器顶栏的视频列表切换到 60 分钟视频，到可编辑，5 次都不超过 3 秒；从 60 分钟视频切回短视频不超过 1 秒。
- **AC-3 转写完成后载入**：60 分钟转写结果返回前端（任一 Provider，测试里用固定的转写结果注入），到字幕列表可编辑，不超过 3 秒。
- **AC-4 滚动**：在 60 分钟数据的「编辑」视图里，用滚轮连续滚动、拖动滚动条从顶部一下拖到底部时，列表内容跟手出现，不出现超过 200 ms 的空白区域；滚动条长度和位置与列表实际长度相符；行号、底部的「总数 / 有效」统计与改动前一致。

**编辑行为不回归**（都在 60 分钟数据上验证）

- **AC-5 编辑后滚走**：当用户修改某一句的文字后把它滚出可视区再滚回来，系统应显示修改后的文字，并且修改照常自动保存到 Host；重新打开项目后修改还在。正在输入的那一句因滚动离开可视区时，已输入的内容不丢失。
- **AC-6 删除与选择**：单句删除、勾选多句后「删除所选」、「全选」（应选中全部未删除的句子，包括不在可视区内的，按钮上的数量与之一致）、「取消选择」、「恢复 (n)」，结果与改动前一致；每个操作从点击到界面更新不超过 300 ms。
- **AC-7 撤销重做**：删除、编辑文字、智能剪空白、批量删除后撤销和重做，结果与改动前一致；撤销一个不在可视区内的句子的修改后，该句内容正确（滚到那里能看到）。
- **AC-8 播放高亮与跟随**：播放或在时间轴上跳转时，当前句的高亮与改动前一致。当前句不在可视区内时，列表应自动把它滚到可视区；用户正在某句文本框里输入，或最近 3 秒内手动滚动过列表时，不自动滚动（高亮照常）。（问题 2，维护者 2026-11-06 按建议确认）
- **AC-9 写回整份字幕的操作**：AI 纠错、翻译、智能剪空白、「原语言」视图确认后写回，列表正确反映结果（包括可视区外的句子），不出现旧内容。
- **AC-10 回归**：F-0002、F-0003 的端到端测试全部通过；短视频（几十句）的「编辑」视图外观和交互与改动前一致（行高、展开 / 收起文本框、勾选、删除按钮、中英文界面、浅色 / 深色）；生产构建载入转写时控制台不再输出字幕全文。

**界面状态**

没有新增界面。打开和切换期间沿用 F-0003 的状态（AC-29「正在打开…」、AC-30 顶栏切换中）。

- **AC-11 载入中**：打开或切换到 60 分钟视频时，「正在打开…」状态一直显示到可编辑为止，不出现「列表空白但界面卡住、点了没反应」的阶段。

## 成功指标

- 版本复盘时对照：AC-1、AC-2 的实测数字（测试报告），以及 2 小时素材的实测数字（只记录）。
- 维护者用自己的 30 分钟以上口播完成一次校对和粗剪，期间没有明显卡顿。
- 发布后 30 天内没有「长视频打开慢 / 卡死」的反馈。

## 约束、风险与影响

- **与已拍板决定**：没有冲突。不改数据格式、RPC 和 Host。
- **隐私**：控制台不再打印字幕全文是正向变化；开发时如需调试输出，改为显式开关（设计阶段定）。
- **浏览器自带的查找（Cmd/Ctrl+F）**：列表只渲染可视部分后，浏览器自带查找找不到可视区外的句子。F-0012 之前，用户现在能用浏览器查找搜全部字幕，改完后搜不到，这是一项退化，见待澄清问题 1。
- **键盘**：现在按 Tab 靠浏览器默认顺序在各句的文本框和按钮之间移动；只渲染可视部分后，Tab 走到可视区边缘时要能继续到下一句（设计阶段定具体做法）。
- **可变行高**：行高随双语 / 单语、文本框展开而变化，设计阶段要处理测量和滚动位置稳定。
- **影响的文档**：`docs/subsystems/frontend.md`（字幕列表的渲染方式）；E-02 Epic 候选表。
- **新依赖**：如果引入列表虚拟化库，按 code-standards 记录理由和体积。

## 待澄清的问题

- [x] 1. **浏览器自带查找退化怎么处理？** 列表只渲染可视部分后，Cmd/Ctrl+F 搜不到可视区外的字幕，F-0012 做出应用内查找之前这段时间是退化。建议：接受，不额外做临时查找框；本需求和 F-0012 尽量在同一个版本发布，发布文档里写明。
  - 维护者 2026-11-06 回答：「Confirm as suggested」，按建议。
- [x] 2. **要不要加播放自动跟随滚动？** 现在的「编辑」视图只有当前句高亮，**没有**自动滚动（代码里没有滚动跟随）。建议：这次加上，因为长列表里当前句很容易在可视区外——播放或时间轴跳转时，当前句离开可视区就把它滚到可视区；用户正在输入，或最近 3 秒内手动滚动过列表时不跟随。确认后把 AC-8 改写成这条规则。也可以选「不加，只保证高亮不回归」，另开需求。
  - 维护者 2026-11-06 回答：「Confirm as suggested」，按建议。
- [x] 3. **「原语言」视图要不要一起提速？** 它是字词级的，60 分钟约 1.5 万个字词，不在打开路径上（默认是「编辑」视图），但切过去可能也很慢。建议：本需求只测量并在测试报告里记录切换到「原语言」视图的耗时，超过 3 秒就在 E-02 补一个候选需求，不在这里做。
  - 维护者 2026-11-06 回答：「Confirm as suggested」，按建议。
- [x] 4. **指标在哪台机器上算？** 建议：以维护者本机 Chrome（Web 端）和本机桌面端为准，测试报告写明机型；不另设低配机器门槛。
  - 维护者 2026-11-06 回答：「Confirm as suggested」，按建议。
