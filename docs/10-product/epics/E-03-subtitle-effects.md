# E-03 字幕样式与特效

## 要解决的问题

口播视频的字幕是观感的一大部分，各平台流行逐字高亮、关键词强调、逐字弹出等动态效果。现在只有静态样式和预设，没有动画。

## 现状（2026-11-05）

- **预览和导出是两套渲染。** 播放器预览用 Canvas 自己绘制（`src/subtitle/subtitleRenderer.ts`），导出时生成 ASS 交给 FFmpeg 的 libass 硬烧（`src/subtitle/burnAss.ts`）。静态样式靠两边各写一遍保持一致，加入动画后很难对齐。
- 已有十几种颜色样式预设、3 种画幅（横屏、9:16、1:1）；烧录进视频的字幕去掉标点。

## 做完是什么样

- 一套预览和导出效果一致的渲染方案，桌面端、Web 端、CLI / MCP 和 Cloud 的导出都能用。
- 口播常用效果：逐字高亮、关键词强调、入场动画。
- 按平台风格的预设库，带平台安全区，横屏、竖屏、方形都可用。
- 用户调好的样式可以存成自己的预设并复用。

## 不做

只能预览、不能导出的效果；手绘关键帧动画编辑器；贴纸、emoji、花字素材库。B-roll 和转场不在 E-03，但 E-03/1 选定的渲染架构要能容纳它们，以后由剪辑线（E-06 / E-07）立项时复用。竖屏短句切分（每屏字数）由 E-01/4 负责。

## E-03/1 要比较的方案

| 方案 | 说明 |
|---|---|
| A. 两层渲染 | 图形层（字幕、动态字幕、标题）用同一份 Canvas 2D 绘制代码，预览在浏览器画，导出在 Host 画（例如 `@napi-rs/canvas`，Skia），透明图层交给 FFmpeg 叠加；剪切、B-roll、转场、编码由 FFmpeg 完成 |
| B. 导出也用网页渲染 | 预览和导出跑同一个网页渲染器，逐帧截图交给 FFmpeg。桌面端用隐藏 WebView，Cloud 用无头 Chromium；参考 Revideo（MIT）、Remotion（公司用户收费） |
| C. Host 端 WebGL 整帧合成 | 参考 FFCreator（MIT，停更约两年，依赖 headless-gl、cairo，Linux 需 Xvfb）。浏览器预览用同类 WebGL 代码 |
| D. libass 预览 | 预览也用 libass（浏览器端 JASSUB，MIT），导出保持 ASS 硬烧；作为基线对照，预期无法支撑复杂动画、图片、B-roll |
| E. Lottie 模板 | 动态字幕以 Lottie JSON 描述，浏览器用 lottie-web，导出端用 Skottie 或 rlottie；可叠加在 A / B / C 之上 |
| 考虑过但不实测 | 自研 Rust 引擎编译到 WASM（工作量过大，作为远期迁移方向记录）；MLT / GStreamer GES（浏览器无法预览，违背两端对齐）；纯 FFmpeg 滤镜（动画能力弱，只作兜底） |

评测维度：

- **一致性**：同一组字幕和动画，预览截图与导出帧的像素差异，macOS（WKWebView）、Windows（WebView2）、Cloud（Linux）三端都测；重点看字体排版（字宽、换行）。
- **导出耗时**：20 分钟和 60 分钟 1080p 口播素材，字幕持续变化时的总耗时与 CPU / 内存。
- **没有界面也能导出**：CLI、MCP、Cloud 托管 Host 是否可用。
- **打包与部署**：安装包体积增量、原生依赖在 macOS / Windows 上的构建难度、Cloud 是否需要 GPU 或 Xvfb。
- **动画能力**：逐字弹出（带回弹缓动）、关键词放大、渐变填充、图片 / emoji。
- **转场的可扩展性**：能否用同一份代码（例如 gl-transitions 的 GLSL）在预览和导出两端实现转场。
- **许可**：禁止商用或对公司收费的方案要标出。

产出：调研报告（02-research）和一份 ADR，写明选定方案、与「桌面导出只走 Host」决定的关系，以及图形层的接口（输入时间点和字幕 / 动画数据，输出一帧）。动画参数用数据描述（关键帧、缓动、按字 / 按词的时间偏移），不写死在绘制代码里，便于以后接入 Lottie 模板或迁移渲染引擎。
