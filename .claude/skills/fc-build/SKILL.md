# 执行阶段：按执行图开发 → 测试 → 验收（节点二）

先读 `docs/00-process/README.md`、`docs/00-process/ai-review.md` 和 `AGENTS.md`。用 `pnpm feature batch status <B-NN>` 看批次状态、波次和「现在可以并行开始」的需求，从那里接着做（换会话接着做时先读批次文件和各需求已有的 02、03 文件）。批次没过方案确认（状态不是 `executing`）就不要开始开发。

单个需求不在任何批次里时（例如小需求单独做），按同样的步骤做，把「批次文件」换成它自己的 04 报告。

**执行期间不等维护者。** 一批里所有需求都完成验收报告并过 AI 审查后，才停一次。

## 什么时候停下来问

只有这几种情况中途停下来问维护者，其他事自己决定，记进「自行决定的事项」：

- 要改需求说明的范围或 AC（加、删、改语义）：改 `01-spec.md`，状态改回 `review`，**只暂停这个需求和依赖它的需求**，其他需求继续；在批次文件里写清楚，等维护者确认（`pnpm feature approve <F> --stage 01-spec --by <维护者>`）。
- 要推翻 `docs/decisions.md` 的决定，或改前面需求已经定好的共用契约。
- 需求一次做不完，需要分几次发布（应该回 Epic 拆需求）。
- 要做不可逆或对外的操作（发版、推送到公共渠道、删除用户数据）。

能等到节点二再问的，写进批次文件「节点二：验收 / 请确认的事项」，不中途停。

## 1. 按执行图调度

1. 执行图的波次就是执行顺序：同一波次的需求并发，下一波次等它依赖的需求的验收报告**通过 AI 审查**再开始（不用等维护者验收）。`pnpm feature batch status` 的「现在可以并行开始」就是当前能派出去的任务。
2. 按批次文件「并发与分派」表派发：
   - 每个需求在自己的分支 / worktree 里做，整个需求一个分支、一个 PR，不在需求内部拆任务。
   - 能交给子代理的，按用户的多模型分工规则派给子代理：同一条消息里并行派发同一波次的需求，每个任务说明自成一体（目标、允许改的文件、接口约定、完成标准、验证命令）。子代理的回报不是证据，主会话自己看 diff、跑测试。
   - 同一波次改到同一批文件的，用独立 worktree，按表里的合入顺序合进集成分支，合入后在集成分支上重跑受影响需求的检查。
3. 每次状态变化都同步：阶段确认、合入集成分支、AI 审查、发现阻塞后，运行 `pnpm feature batch sync <B-NN>`；分派或执行者有变化，更新「并发与分派」表。执行图是维护者看进度的地方，必须和实际一致。

## 2. 开发（03-implementation.md）

1. 遵守 `docs/code-standards.md` 全部验收标准。
2. 按实现清单推进，每完成一项：
   - 跑验证计划里这一项的检查；
   - 提交一次，commit 正文带 Verification 段，并加一行 `Refs: <F-编号>/AC-n`；
   - 在 `02-design.md` 勾选这一项，在 `03-implementation.md` 的进度表追加一行（日期、清单项、提交、检查）。
3. 测试名称带 AC 编号，例如 `F-0001/AC-3 ……`。界面直接写真实代码，接真实的 stores 和 Host，不另做原型或假数据版本；涉及界面的 AC，按目标平台写端到端测试，和代码一起提交。
4. 清单的顺序和粒度、设计里的实现细节可以按实际调整，写进「与设计的偏差」。
5. 清单全部勾选后 `pnpm feature review <F-编号>`（脚本检查清单并自动确认），`batch sync`。

## 3. 测试与验收（04-test-report.md）

1. 在一个固定的 commit 上验收，把 sha 写在报告开头；之后代码有改动就重新验收。
2. 逐条验证每一条 AC：
   - 自动测试：写出测试名和命令。
   - 涉及界面的 AC：先在目标平台跑端到端测试，测试名带 AC 编号；覆盖需求说明写到的每个界面状态和明暗主题，断言关键文字和可操作的控件。Web 现用 Playwright（`tests/e2e/features/<F-编号>.spec.ts`）；可用 `page.route` 构造异常状态，需要真实 Host 时用 `pnpm dev` 并注明。桌面专属行为不得用 Web 通过代替。
   - Web 界面证据用 `shot()` 和 `pnpm e2e:evidence <F-编号>`：截图写进 `screenshots/`（进 git），录屏和摘要写进 `recordings/`（只在本地）。桌面证据注明应用构建和运行平台。
   - 修 bug 类的 AC 做 Red check：撤掉修复后测试必须失败。
   - 需要真实使用的 AC（真实模型、真实视频、Tauri 桌面端、真实 API），优先自动化驱动真实环境；只有现有自动化无法验证的步骤才用 Computer Use 或人工补验，记录原因、步骤和观察结果。
   - 做不到的写 `⏸ Not run` 和原因，**不能省略或写成通过**。
3. 回归检查：跑 `docs/code-standards.md` 第 1、2 条的全部命令，记录结果。
4. 测试没通过：回到开发修复，再重新验收，不要把 ❌ 留给维护者。修不了的写清原因。
5. 填写「设计与实现摘要」「自行决定的事项」（汇总 02、03 里记下的每一条，需要拍板的标「请确认」）、「界面证据」，结论写「可以发布」或「需要修复后重测」。
6. 独立 AI 审查员按 `ai-review.md` 的「04-test-report」清单审，**审查员自己重跑报告里的自动化命令和一个 Red check**。通过后 `pnpm feature ai-review <F> --by <审查员>`，再 `pnpm feature review <F>`，`batch sync`。这时依赖它的下一波次需求就可以开始了。

## 4. 汇总到批次文件，停下来：节点二

所有需求都到了 `04-test-report: review`（spike 调研已由 AI 确认），`pnpm feature batch status` 显示 `acceptance-review` 后，填写批次文件「节点二：验收」：

- 每个需求的结论、AC 通过数、验收报告链接；
- 所有 Not run 及原因；
- 请确认的事项（各需求「请确认」的自行决定、执行中记下的待问事项）；
- AI 已确认的事项：调研结论、未标「请确认」的自行决定，一句话一条，维护者可以抽查。

把批次文件、各报告和主要截图 / 录屏发给维护者（有 SendUserFile 就用它），用几句话总结结果、Not run 项和请确认的事项。**一批只停这一次。**

## 验收确认

- **不要自己运行 `approve`。** 维护者明确确认后才运行 `pnpm feature approve <B-NN> --by <维护者>`，同时把批次里列出的 `proposed` ADR 改为 `accepted`，再 `batch sync`。
- 维护者只退回部分需求：只修这些需求和依赖它们的需求，重新验收、AI 审查、`batch sync`，其余已通过的可以单独 `pnpm feature approve <F...> --by <维护者>`。
- 验收通过后需求就完成了，留在「待发布」列表里，发版时由 `fc-release` 一起带上。
