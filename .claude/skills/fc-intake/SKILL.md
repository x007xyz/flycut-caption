# 阶段 0–1：需求收集与立项

1. 先用 `pnpm feature status` 检查是否已有相同的需求；有就沿用，不重复立项。
2. 找到它属于哪个 Epic（`docs/10-product/epics/`），以及对应的候选编号（例如 E-05/2）。Epic 还没确认，或 Epic 里没有对应的候选，停下来告诉维护者，先用 `fc-plan` 补充 Epic。
3. 新建：`pnpm feature new <英文-slug> "<中文标题>" --epic E-NN`，技术调研加 `--type spike`，有依赖加 `--depends F-0002,F-0003`（Epic 里候选依赖已经立项的，写对应的 F-编号）。然后在 Epic 文档的「需求编号」列回填新编号。
4. 按模板填写 `01-intake.md`：
   - 来源：issue 链接或用户原话，**原样引用**，注明日期。
   - 要解决的问题：只写问题，不写方案。
   - 优先级：对照 `docs/decisions.md` 的 P0–P4，说明属于哪一级、为什么现在做。
   - 约束与风险：特别检查是否与 `docs/decisions.md` 已拍板的决定冲突，以及授权、隐私问题。
   - 目标用户、竞品怎么做、获客价值：对照 `docs/10-product/vision.md`，写清楚是哪类口播创作者、竞品（剪映、Descript、Gling、OpusClip 等）在这件事上怎么做、我们的不同、能对应哪个获客渠道。竞品资料要写来源和日期，查不到的写「待核实」，不要编造。
   - 依赖：说明依赖哪些需求或任务、为什么。
   - 规模检查：逐项勾选；有一项不满足，在结论里建议退回 Epic 拆分。
   - 待澄清的问题：列出你需要维护者回答的问题，不要自己假设答案。
5. 「结论」一节写你的建议（做 / 待澄清 / 不做），由维护者最终确认。

## 通用规则

- 先读 `docs/00-process/README.md`（阶段、编号、闸门）和 `AGENTS.md`。
- 用 `pnpm feature status <F-编号>` 确认当前阶段就是本阶段且状态是 `draft`；不是就停下，告诉维护者当前状态和下一步。
- 只编辑本阶段的文件。发现前面阶段的文档有错，停下来告诉维护者，由维护者决定是否退回修改。
- 写完后运行 `pnpm feature review <F-编号>`，然后**停下来请维护者确认**，用几句话总结本阶段的要点和待决问题。
- **不要自己运行 `approve` 或 `skip`。** 只有维护者在对话里明确确认（例如「确认」「通过」「可以进入下一步」）后，才运行 `pnpm feature approve <F-编号> --by <维护者>`，再运行 `pnpm feature next <F-编号>`。维护者说本阶段不需要时，才用 `skip`，并写明原因。
