# 阶段 2：产品文档

1. 读本需求的 `01-intake.md`、`docs/decisions.md`、`docs/10-product/` 下的相关规格。
2. 填写 `02-prd.md`：
   - 范围分「做」和「不做」，「不做」和「做」一样重要。
   - 验收标准每条一个编号 `AC-n`，写成可验证的句子（当……时，系统应……），注明在哪个界面（Web / 桌面）和哪种 Provider 下成立。每条都要能在阶段 6 被测试或真实使用验证。
   - 涉及界面的：每个新增或改动的界面，每个状态（空、加载中、正常、出错、冲突……）各写一条 AC，写明用户看到什么、能做什么、关键文案（中英文）。不再有单独的原型阶段，状态在这里没写就不会被设计和测试覆盖。方向不清楚的新页面，可以先做一次性的 HTML 或 Artifact 页面给维护者看，看完就扔，结论写进 PRD。
   - 成功指标写上线后可以观察到的东西，阶段 9 复盘要对照。
3. 「拆分检查」：验收标准超过 10 条左右，或「做」里有几件可以单独发布的事，就停下来建议维护者拆成多个需求，说明怎么拆，不要硬写成一个 PRD。
4. 立项中「待澄清的问题」如果还没有答案，列在「未决问题」里，不要自己替维护者决定。

## 通用规则

- 先读 `docs/00-process/README.md`（阶段、编号、闸门）和 `AGENTS.md`。
- 用 `pnpm feature status <F-编号>` 确认当前阶段就是本阶段且状态是 `draft`；不是就停下，告诉维护者当前状态和下一步。
- 只编辑本阶段的文件。发现前面阶段的文档有错，停下来告诉维护者，由维护者决定是否退回修改。
- 写完后运行 `pnpm feature review <F-编号>`，然后**停下来请维护者确认**，用几句话总结本阶段的要点和待决问题。
- **不要自己运行 `approve` 或 `skip`。** 只有维护者在对话里明确确认（例如「确认」「通过」「可以进入下一步」）后，才运行 `pnpm feature approve <F-编号> --by <维护者>`，再运行 `pnpm feature next <F-编号>`。维护者说本阶段不需要时，才用 `skip`，并写明原因。
