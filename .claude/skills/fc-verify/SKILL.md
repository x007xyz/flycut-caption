# 阶段 6：测试与验收

1. 在一个固定的 commit 上验收，把 sha 写在报告开头；之后代码有改动就重新验收。
2. 逐条验证 `02-prd.md` 的每一条 AC：
   - 自动测试：写出测试名和命令。
   - 涉及界面的 AC：必须有 Playwright 端到端测试，放在 `tests/e2e/features/<F-编号>.spec.ts`，测试名带 AC 编号。
     - 覆盖 PRD 写到的每个界面状态，明暗主题各跑一遍；断言关键文字和可操作的控件，不只截图。
     - 需要 Host 的状态用 `page.route` 拦截 Host 请求构造；必须真实运行 Host 的，在测试里注明并用 `pnpm dev` 跑。
     - 测试里用 `tests/e2e/lib/evidence.ts` 的 `shot(page, '<F-编号>', '<界面>-<状态>-<主题>')` 在每个状态截图。
     - 运行 `pnpm e2e:evidence <F-编号>`：跑测试，截图写进需求目录的 `screenshots/`，每个测试的录屏写进 `recordings/`（本地查看，不进 git），结果摘要在 `recordings/summary.json`。
     - 截图之外，用内置浏览器把主流程实际点一遍，发现测试没覆盖的问题记在「发现的问题」。
   - 修 bug 类的 AC 做 Red check：撤掉修复后测试必须失败。
   - 需要真实使用的 AC（真实模型、真实视频、Tauri 桌面端、真实 API），实际操作一遍并记录结果，必要时截图放在需求目录。
   - 做不到的写 `⏸ Not run` 和原因，**不能省略或写成通过**。
3. 回归检查：跑 `docs/code-standards.md` 第 1、2 条的全部命令，记录结果。
4. 测试没通过：回到开发修复，再重新验收，不要把 ❌ 留给维护者。修不了的（例如环境问题）写清原因。
5. 填写报告里给维护者看的部分：
   - 「设计与实现摘要」：几句话说明方案、关键取舍、新写的 ADR、与设计的偏差；
   - 「自行决定的事项」：汇总技术设计和开发阶段记下的每一条；
   - 「界面证据」：按界面和状态列出截图和录屏的路径。
6. 结论写「可以发布」或「需要修复后重测」。有 Not run 时，由维护者决定是否接受。
7. 运行 `pnpm feature review <F-编号>`，然后**停下来请维护者确认**。把报告、截图和主要录屏发给维护者（有 SendUserFile 就用它发送，否则列出路径），用几句话总结结果、Not run 项和需要维护者拍板的自行决定事项。

## 通用规则

- 先读 `docs/00-process/README.md`（阶段、编号、闸门）和 `AGENTS.md`。
- 用 `pnpm feature status <F-编号>` 确认当前阶段就是本阶段且状态是 `draft`；不是就停下，告诉维护者当前状态和下一步。
- 测试失败可以回去改代码和设计文档，改动记进 `05-implementation.md`。发现 PRD 本身有错，停下来告诉维护者。
- **不要自己运行 `approve` 或 `skip`。** 只有维护者在对话里明确确认（例如「确认」「通过」「可以进入下一步」）后，才运行 `pnpm feature approve <F-编号> --by <维护者>`，再运行 `pnpm feature next <F-编号>`；同时把报告里列出的 `proposed` ADR 改为 `accepted`。维护者要求修改时，回到开发修复后重新验收。本阶段不能跳过。
