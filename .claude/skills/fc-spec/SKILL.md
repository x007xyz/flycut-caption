# 方案阶段：需求说明 + 技术设计 + 执行图（节点一）

先读 `docs/00-process/README.md`、`docs/00-process/ai-review.md` 和 `AGENTS.md`。

维护者只在两个时间点集中审：方案确认、验收。所以这一步要把一批需求的**需求说明和技术设计都写完、都过 AI 审查、建好执行图**，再停一次。中间不为单个需求停下来。

## 1. 立项

1. `pnpm feature status` 检查是否已有相同的需求；有就沿用，不重复立项。
2. 找到每个需求属于哪个 Epic（`docs/10-product/epics/`）和候选编号（例如 E-05/2）。Epic 里没有对应候选：小的直接在 Epic 候选表里补一行；大的先用 `fc-plan` 拆。Epic 和产品文档的改动不单独请维护者确认，记下编号，放进批次的 `--docs` 一起确认。
3. 新建：`pnpm feature new <英文-slug> "<中文标题>" --epic E-NN`，技术调研加 `--type spike`，有依赖加 `--depends F-0002,F-0003`。在 Epic 文档的「需求编号」列回填新编号。

## 2. 需求说明（01-spec.md）

按模板填写：

- 来源：issue 链接或用户原话，**原样引用**，注明日期。
- 要解决的问题：只写问题，不写方案；对照 `docs/10-product/vision.md` 写清楚是哪类口播创作者。
- 竞品与获客：资料写来源和日期，查不到的写「待核实」，不要编造。小需求一两句即可。
- 优先级与依赖：对照 `docs/decisions.md` 的 P0–P4。
- 范围分「做」和「不做」。
- 验收标准每条一个编号 `AC-n`，写成可验证的句子（当……时，系统应……），注明界面（Web / 桌面）和 Provider。涉及界面的，每个新增或改动的界面、每个状态（空、加载中、正常、出错、冲突……）各写一条 AC，写明用户看到什么、能做什么、关键文案（中英文）。方向不清楚的新页面，可以先做一次性的 HTML 或 Artifact 页面，结论写进来，页面链接放进批次文件。
- 调研类需求（spike）不写 AC，在「验收标准」一节改写「要回答的问题」。
- 约束、风险与影响：检查是否与 `docs/decisions.md` 冲突，以及授权、隐私问题。
- 规模检查：AC 超过 10 条左右，或「做」里有几件可以单独发布的事，在结论里建议怎么拆。
- 待澄清的问题：列出要维护者回答的问题，不要自己假设答案；每个问题给出建议答案。**不要因为有待澄清问题就停下**：按建议答案继续写设计，在设计里标明哪些地方依赖这个答案。

写完：独立 AI 审查员按 `ai-review.md` 的「01-spec」清单审（见下面「AI 审查」），通过后 `pnpm feature ai-review <F> --by <审查员>`，再 `pnpm feature review <F>`。脚本会把它改成 `review` 并立即创建 `02-design.md`。

## 3. 技术设计（02-design.md，功能类需求）

1. 按 `AGENTS.md` 的路由表读涉及的子系统文档和 `docs/20-architecture/`。
2. 填写：
   - UI/UX：改哪些组件、新增哪些组件、接哪些 stores 和 RPC，每个界面状态怎么在端到端测试里构造。没有界面改动写「无界面改动」。
   - 技术方案：遵守子系统文档的规则，写出至少一个备选方案和取舍。没有架构变化时可以写得很短。
   - 「验收标准覆盖」表覆盖每一条 AC。
   - 「实现清单」：按功能纵向切、按依赖顺序排，一般 3–8 项；几个需求共用的契约放在第一项里定好。
   - 「验证计划」：按 `docs/30-engineering/acceptance-testing.md` 逐条 AC 写目标平台、自动化命令和断言。
3. 需要长期遵守的架构决定：`pnpm feature adr <slug> "<标题>" --feature <F-编号>`，状态 `proposed`，列进批次文件。
4. 独立 AI 审查（「02-design」清单）→ `pnpm feature ai-review` → `pnpm feature review`。

spike 不写设计，01-spec 过审后就算方案就绪；调研本身在方案确认后用 `fc-research` 做。

## 4. 批次与执行图

一批需求的方案都写完后（可以边写边建），建批次：

```bash
pnpm feature batch new <slug> "<标题>" F-0060 F-0061 F-0062 [--docs E-05,ROADMAP]
```

脚本按 `depends_on` 生成 Mermaid 执行图（方案并行 → 节点一 → 按依赖分的波次 → 节点二）和进度表。然后手工填写批次文件：

- **目标与范围**：这一批要达成什么，为什么这几个放在一起。
- **并发与分派**：每个需求一行，写波次、分支 / worktree、执行者（主会话，或哪个子代理；按用户的多模型分工规则）、合入集成分支的顺序。同一波次里会改同一批文件的需求，要么各自用独立 worktree 并写明合入顺序，要么在设计里调整依赖、放到不同波次。
- **节点一：方案确认**：每个需求一句话方案和 AC 数；所有待澄清的问题和建议答案（标需求编号）；Epic / 产品文档改动；新写的 ADR；AI 审查结论，以及两轮没审过、要维护者拍板的问题。

`pnpm feature batch sync <B-NN>`，`pnpm feature batch status <B-NN>` 确认状态是 `plan-review`。

### 并行写方案

几个需求的需求说明和设计互不依赖，可以并行派给子代理写，每个子代理只碰自己需求目录下的文件；Epic 文档和批次文件由主会话统一改。子代理写完由另一个子代理审，主会话看审查结果、核对后再记录 `ai-review`。

## AI 审查

- 写文件的不审自己的：另起子代理，只给它文件路径和 `docs/00-process/ai-review.md` 对应清单，让它自己读代码核对。
- 不通过就改完再审，最多两轮；两轮还不过，写进批次文件留给维护者。
- 审查员能确认的（格式、措辞、清单顺序、测试写法、实现细节）就不要留给维护者。

## 停下来：节点一

把批次文件发给维护者（有 SendUserFile 就用它），用几句话说明：这一批有哪些需求、执行图分几个波次、哪些可以并发、待澄清问题和建议答案、需要拍板的事。**一批只停这一次。**

## 确认

- **不要自己运行 `approve`。** 维护者在对话里明确确认（例如「确认」「按建议」「B-03 通过，F-0061 的 AC-4 改成……」）后：先把待澄清问题的答案和维护者的修改写回对应文件（修改后的文件再过一次 AI 审查），再运行 `pnpm feature approve <B-NN> --by <维护者>`。
- approve 后脚本创建 `03-implementation.md`（依赖已满足的）和 spike 的 `02-research.md`。维护者没说「先别做」就直接用 `fc-build` 按执行图执行。
- 维护者只改了几条：改完重新 AI 审查、`batch sync`，不需要再整批重审，除非改动影响执行图。
