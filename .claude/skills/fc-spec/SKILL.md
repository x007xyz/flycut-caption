# 需求说明（01-spec）

维护者一个人从需求做到开发，所以立项和 PRD 合成一份文件、确认一次。写的时候想清楚「要不要做」和「做成什么样」，不要把问题留到设计阶段。

1. 先用 `pnpm feature status` 检查是否已有相同的需求；有就沿用，不重复立项。
2. 找到它属于哪个 Epic（`docs/10-product/epics/`）和候选编号（例如 E-05/2）。Epic 里没有对应候选：小的直接在 Epic 候选表里补一行，在总结里告诉维护者；大的先用 `fc-plan` 拆。
3. 新建：`pnpm feature new <英文-slug> "<中文标题>" --epic E-NN`，技术调研加 `--type spike`，有依赖加 `--depends F-0002,F-0003`。在 Epic 文档的「需求编号」列回填新编号。
4. 按模板填写 `01-spec.md`：
   - 来源：issue 链接或用户原话，**原样引用**，注明日期。
   - 要解决的问题：只写问题，不写方案；对照 `docs/10-product/vision.md` 写清楚是哪类口播创作者。
   - 竞品与获客：资料写来源和日期，查不到的写「待核实」，不要编造。小需求一两句即可。
   - 优先级与依赖：对照 `docs/decisions.md` 的 P0–P4。
   - 范围分「做」和「不做」，「不做」和「做」一样重要。
   - 验收标准每条一个编号 `AC-n`，写成可验证的句子（当……时，系统应……），注明界面（Web / 桌面）和 Provider。涉及界面的，每个新增或改动的界面，每个状态（空、加载中、正常、出错、冲突……）各写一条 AC，写明用户看到什么、能做什么、关键文案（中英文）。没有单独的原型阶段，状态在这里没写就不会被设计和测试覆盖。方向不清楚的新页面，可以先做一次性的 HTML 或 Artifact 页面给维护者看，结论写进来。
   - 调研类需求（spike）不写 AC，在「验收标准」一节改写「要回答的问题」。
   - 约束、风险与影响：特别检查是否与 `docs/decisions.md` 已拍板的决定冲突，以及授权、隐私问题。
   - 规模检查：逐项勾选；AC 超过 10 条左右，或「做」里有几件可以单独发布的事，在结论里建议怎么拆，不要硬写成一个需求。
   - 待澄清的问题：列出要维护者回答的问题，不要自己假设答案；每个问题给出你的建议答案，方便维护者直接说「按建议」。
5. 运行 `pnpm feature review <F-编号>`，**停下来请维护者确认**。

## 一次写一批

规划好一个阶段要做的几个需求时，一次把它们的需求说明都写完、都 `review`，再停下来：

- 用一张表总结：编号、标题、AC 数、依赖、待澄清的问题和你的建议答案。表格直接写在回复里，不另建审阅文件。
- 维护者可以一次确认全部，也可以只指出要改的几条。

## 确认

- **不要自己运行 `approve`。** 维护者在对话里明确确认（例如「确认」「通过」「F-0006 到 F-0009 都按建议」）后，才运行 `pnpm feature approve <F-编号...> --by <维护者>`（可以一次写多个编号）。待澄清问题的答案先写回 `01-spec.md` 再 approve。
- approve 后脚本自动创建下一阶段文件：功能是 `02-design.md`，接着用 `fc-build` 连续做完设计、开发和验收；调研是 `02-research.md`，用 `fc-research`。维护者没说「先别做」就直接接着做。
- 维护者要求修改：改完重新 `pnpm feature review`（状态在 review 时直接改文件即可）。
