# 阶段 3：技术设计

1. 读 `02-prd.md`，再按 `AGENTS.md` 的路由表读涉及的子系统文档和 `docs/20-architecture/`。
2. 填写 `03-design.md`：
   - UI/UX：界面状态和文案以 PRD 的 AC 为准，这里写改哪些组件、新增哪些组件、接哪些 stores 和 RPC，以及每个界面状态怎么在端到端测试里构造出来（拦截 Host 请求还是真实运行 Host）。没有界面改动写「无界面改动」。PRD 漏了某个界面状态时，按最合理的方式补进设计，记进「自行决定的事项」。
   - 技术方案：遵守子系统文档的规则（例如新 RPC 由插件注册并在 `shared/protocol.ts` 声明、Tauri 只做外壳）。写出至少一个备选方案和取舍。
   - 「验收标准覆盖」表必须覆盖 PRD 的每一条 AC。
   - 「实现清单」：开发阶段按它推进，不再拆任务。每项是一段能单独验证的功能，按功能纵向切（从存储到界面打通），不按技术层切；按依赖顺序排，一般 3–8 项。几个需求共用的契约（数据格式、RPC、存储结构）放在第一项里定好。
   - 「验证计划」：每项完成时要跑的检查（对照 `docs/code-standards.md`），涉及界面的 AC 对应哪些端到端测试，哪些 AC 需要真实使用验证。
   - 清单写不下、或者需要分几次发布时，停下来建议维护者回 Epic 拆需求。
   - 需要长期遵守的架构决定照常写 ADR（状态 `proposed`），不等确认，在测试报告里列出由维护者一并确认。
3. 需要长期遵守的架构决定，用 `pnpm feature adr <slug> "<标题>" --feature <F-编号>` 新建 ADR，状态保持 `proposed`，在设计文档里链接；维护者确认测试报告时一并改为 `accepted`。
4. 本阶段不能跳过：没有架构变化时，技术方案可以写得很短，但实现清单和验证计划必须有。

## 通用规则

- 先读 `docs/00-process/README.md`（阶段、编号、闸门）和 `AGENTS.md`。
- 用 `pnpm feature status <F-编号>` 确认当前阶段就是本阶段且状态是 `draft`；不是就停下，告诉维护者当前状态和下一步。
- **技术设计 → 开发 → 测试与验收由 agent 连续推进，中间不等维护者确认。** 本阶段写完后运行 `pnpm feature review <F-编号>`：检查通过会自动确认（`approved_by: auto`），接着运行 `pnpm feature next <F-编号>` 进入下一阶段，继续用对应的 Skill 做下去。维护者在「测试与验收」时一并审阅设计、实现和测试结果。
- 不要用 `approve` 或 `skip`；`skip` 只在维护者明确说本阶段不需要时使用。
- 「自行决定的事项」逐条记下（决定了什么、为什么、影响哪条 AC），测试报告会汇总给维护者。
